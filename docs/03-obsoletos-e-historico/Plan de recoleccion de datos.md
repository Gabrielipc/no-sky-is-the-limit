# Plan de recolección de datos a mayor escala

Fecha: 5 de noviembre de 2026. Este documento prepara la recolección; no afirma que se haya descargado ni validado el catálogo. Alcance confirmado: Luna y regiones polares desde el primer lote; almacenamiento local disponible de 50–100 GB. Alcance de trabajo propuesto: nivel B de [Arquitectura para el hackathon](Arquitectura%20para%20el%20hackathon.md), con Tierra, Marte y Luna, relieve como núcleo y otras dimensiones como contexto. Es una hipótesis de planificación, no una decisión científica. La visión completa y los datos sorpresa del evento requieren una revisión posterior. Verificar primero las reglas del evento sobre preparación previa.

## Diseño del script de retrieval

Propuesta: un comando Pixi/Python `scripts/recolectar_datos.py` con adaptadores por proveedor y un catálogo declarativo en `specs/sources/`; no reutilizar el script de procesamiento existente. Ejemplos de interfaz propuestos, todavía no implementados:

```sh
pixi run python scripts/recolectar_datos.py doctor
pixi run python scripts/recolectar_datos.py discover --profile base --out data/manifests/plan.json
pixi run python scripts/recolectar_datos.py fetch --plan data/manifests/plan.json --max-gb 20
pixi run python scripts/recolectar_datos.py verify --plan data/manifests/plan.json
```

1. `doctor`: comprobar espacio libre, conectividad y acceso a proveedores; identificar cuentas necesarias sin mostrar credenciales. No falla todo el plan por un proveedor opcional.
2. `discover`: consultar índices PDS y enlaces oficiales USGS o API del proveedor, con paginación cuando aplique; fijar producto, versión, archivos, etiquetas y documentación asociados. Para AOI, registrar geometría, selección y cobertura solicitada. Emitir plan con número de archivos, tamaños conocidos y desconocidos, derechos pendientes y necesidades de acceso. No descargar datos grandes.
3. `fetch`: consumir un plan explícito; descargar a un área temporal con límites de concurrencia, reintentos, tiempos de espera, reanudación solo cuando el servidor la soporte y validación de tamaño/respuesta. Evitar tratar páginas HTML de login como datos. Registrar cambios de URL o versión y no sobrescribir ni borrar originales. Si el destino ya existe, verificar identidad; si difiere, conservar ambas versiones y registrar conflicto. Permitir una fuente o perfil por vez y límite de presupuesto.
4. `verify`: calcular SHA-256, comprobar tamaños, respuesta y checksums publicados cuando existan; inspeccionar etiquetas y estructura con GDAL/PDS sin atribuir autenticidad a hashes generados localmente. Guardar fallos y ausencias como tales. No normalizar ni generar métricas científicas en retrieval.
5. Guardar manifiesto por ejecución: identificador/versiones de producto, origen y URL sin secretos, fecha UTC, proveedor, AOI y parámetros, archivo, tamaño, SHA-256 local, hash oficial si existe, resultado de comprobación, atribución, licencia y estado (verificada/pendiente), etiquetas, errores y versión de herramienta. Mantener un resumen de cobertura faltante y una lista para reanudar; registrar también fuentes que no pudieron consultarse.
6. Destino propuesto `data/raw/<fuente>/<version>/<archivo>` y manifiestos separados en `data/manifests/`. No migrar ni alterar los datos existentes automáticamente; registrar su reutilización solo tras comprobar hash y correspondencia con el catálogo remoto. Considerar espacio para archivos temporales, descompresión y derivados por separado.

**Seguridad y acceso:** autenticarse por mecanismos oficiales del proveedor (inicio de sesión del usuario, almacén local o variables de entorno según su documentación); nunca pedir contraseñas o tokens por el chat, guardarlos en manifests ni imprimir cabeceras de autorización. Las cuentas Earthdata y USGS pueden ser distintas. No se requiere una cuenta para empezar a investigar los índices públicos de PDS; confirmar requisitos por endpoint durante `doctor`. Para accesos con formularios, acuerdos o licencias, detener solo ese adaptador e indicar al usuario la página y acción concretas.

## Orden de trabajo y controles

1. Confirmar reglas del evento, espacio de destino y disponibilidad del servidor. Ejecutar discovery y cuantificar bytes reales antes de la descarga; mantener desconocidos explícitos. Comprobar que el presupuesto incluye temporales y datos descomprimidos.
2. Seleccionar productos y obtener metadatos primero: índice completo MOLA incluyendo polos; GMTED por estadística con mapa de fuentes y cobertura; LOLA y etiquetas reales. Contrastar nombres y versiones con el proveedor. La [publicación GMTED](https://pubs.usgs.gov/of/2011/1073/pdf/of2011-1073.pdf) da tamaños históricos de ~4,5–4,6 GB para varias mallas de 7,5″; no garantiza el tamaño actual transferido ni el espacio descomprimido. El presupuesto de la arquitectura es una estimación no verificada.
3. Probar descarga y reanudación con archivos pequeños y un subconjunto representativo; inspeccionar etiquetas, hashes y errores. En particular resolver la discrepancia MOLA y verificar la interpretación de escala/offset de cada etiqueta LOLA antes de usar las imágenes.
4. Descargar por lotes los conjuntos núcleo, comprobando inventario, integridad y cobertura; recuperar por separado los datos de regiones polares. La elección de estadística GMTED y fuentes polares requiere revisión del equipo.
5. Completar catálogo de sitios y luego añadir fuentes contextuales en orden de utilidad y condiciones de uso. Comprobar que cada paquete incluya leyendas, fechas, restricciones y referencias. Documentar faltantes sin sustituirlos por cero.
6. Preparar informe de cobertura y procedencia por cuerpo y fuente, con archivos ausentes, espacio real, licencias pendientes y errores. El pipeline analítico, los contratos y la validación de resultados son etapas posteriores.

## Decisiones o información necesarias

- Confirmado: Luna y regiones polares se incluyen desde el primer lote; se dispone de 50–100 GB de almacenamiento local. El espacio libre real y la ubicación concreta deben comprobarse antes de ejecutar descargas. Las capas contextuales se mantienen en lotes posteriores.
- Para el primer plan usar un límite conservador de 50 GB incluyendo originales, parciales, manifiestos y extracción temporal; los 100 GB son un techo disponible, no una reserva comprobada. Detener antes de exceder el límite o el espacio libre; no contar con el servidor de 500 GB de la arquitectura.
- Seleccionar AOI o procedimiento de curación para sitios de referencia; decidir productos terrestres/polares y estadística GMTED con revisión científica.
- Si un proveedor exige cuenta o aceptación de términos, solicitar al usuario únicamente que complete el paso oficial y configure acceso local; verificar después sin pedir secretos en el chat. Aún no se ha comprobado que sea imprescindible para el primer lote concreto.

## Ajuste confirmado: primer lote con Luna y polos

- **Marte:** inventariar en PDS tanto las teselas MEG128 de topografía/recuentos como los productos polares norte y sur a 128 píxeles/grado, junto con sus etiquetas y `DSMAP_POLAR.CAT`. La [guía MOLA](https://pds-geosciences.wustl.edu/missions/mgs/megdr.html) distingue explícitamente los mapas polares. Seleccionar archivos tras consultar el índice vigente, sin suponer continuidad entre proyecciones.
- **Luna:** incluir LOLA GDR global desde el primer lote, etiquetas y documentación; confirmar por metadatos si se requieren productos polares adicionales y qué datos de soporte existen. La variante `ldem_64_float` es una candidata, no una decisión sobre calidad o referencia vertical.
- **Tierra:** incluir GMTED2010 7,5″ y adquirir también un candidato de cobertura polar desde el inicio. Como primera alternativa de baja resolución, examinar GMTED 30″ media o muestreo sistemático: [USGS](https://www.usgs.gov/centers/eros/science/usgs-eros-archive-digital-elevation-global-multi-resolution-terrain-elevation) indica cobertura polar para algunos productos, pero no garantiza cobertura de toda tierra al norte de 84° N. Inventariar y seleccionar un complemento para el norte extremo, y verificar vacíos efectivos de Groenlandia y Antártida. [USGS describe ArcticDEM y RAMP](https://www.usgs.gov/landsat-missions/landsat-collection-2-digital-elevation-model) como fuentes polares candidatas; todavía hay que verificar distribución, tamaño, condiciones y resolución antes de elegir archivos concretos. No se considera cumplida la cobertura polar hasta comprobarla con los datos y sus máscaras.
- **Presupuesto:** comenzar con un presupuesto efectivo máximo de 50 GB, reservando espacio para archivos parciales y extracción, y mostrar el total conocido, el desconocido y el espacio libre antes de cada lote. No se ha medido el disco local ni validado el tamaño de los paquetes; no se promete que todos los originales y temporales quepan hasta completar el inventario remoto.
